# FR-015: Export scheduler metrics for Prometheus and ix-board

## Description

The scheduler SHALL export per-host metrics in Prometheus text format and as the versioned JSON snapshot ix-board reads, so that queue wait, configured and sustainable slot capacity, pause time, admission blocking, and disk use can be seen for every host, including builds observed after an external wrapper admits them.

## Behavior

The supervised governor (`locked-build serve`, [FR-010](FR-010-scheduler-owned-throttling.md)) serves the Prometheus text over HTTP at `--listen ADDR`, bound to loopback unless told otherwise; it is the same process that samples and throttles. `metrics` writes the same text to standard output or atomically to a file for a textfile collector when the governor is down. The JSON status snapshot of FR-005 carries the same values. Series, labelled by `host` unless noted:

| Series | Type | Extra labels |
|---|---|---|
| `ix_build_queue_depth` | gauge | `priority` |
| `ix_build_queue_wait_seconds` | histogram | `priority` |
| `ix_build_slots_busy`, `ix_build_slots_configured`, `ix_build_slots_sustainable`, `ix_build_slots_max` | gauge | none |
| `ix_build_pause_seconds_total` | counter | `reason` (`thermal`, `operator`) |
| `ix_build_admission_blocked_seconds_total` | counter | `reason` (`memory`, `swap`, `compressor`, `host_load`, `target_disk`, `operator`, `probe`) |
| `ix_build_paused_orphans` | gauge | none |
| `ix_build_probe_defect` | gauge | `probe` |
| `ix_build_agent_processes`, `ix_build_agent_rss_bytes` | gauge | none |
| `ix_build_builds_total` | counter | `priority`, `outcome` |
| `ix_build_test_runs_total` | counter | `outcome` |
| `ix_build_target_dir_bytes`, `ix_build_target_dir_slots` | gauge | `repo` |
| `ix_build_probe_value`, `ix_build_probe_unavailable` | gauge | `probe` |
| `ix_build_lane_running` | gauge | `lane` |

The `lane` label is the bounded lane address `server:workspace:tab` of [FR-011](FR-011-priority-classes-lane-fair-share.md), never a session id. At most `max_lane_labels` (default 64) distinct lanes are labelled; others are summed under `other`. Until the SWM-239 TOML profile exists, `ix_build_slots_configured` for an admitted store is sourced from the `capacity_units` field in the locked-build per-host JSON host policy. After that profile exists, it is sourced from TOML `[host].max_slots`. It is a configured server-capacity value in either state; no sustainable value is derived from it. FR-009's sustainable slot count is computed separately from its TOML profile and live probes, and is unavailable before that profile exists. A series with no producer in the current build is absent until its producer exists, never exported as zero. The current locked-build implementation emits six metric names from this table: `ix_build_queue_depth`, `ix_build_queue_wait_seconds`, `ix_build_slots_busy`, `ix_build_slots_configured`, `ix_build_builds_total`, and `ix_build_admission_blocked_seconds_total`. The complete current-build absence set includes these 11 additional metric names from the table: `ix_build_slots_max`, `ix_build_paused_orphans`, `ix_build_probe_defect`, `ix_build_agent_processes`, `ix_build_agent_rss_bytes`, `ix_build_test_runs_total`, `ix_build_target_dir_bytes`, `ix_build_target_dir_slots`, `ix_build_probe_value`, `ix_build_probe_unavailable`, and `ix_build_lane_running`. It also includes `ix_build_pause_seconds_total` until a pause-time producer exists, `ix_build_slots_sustainable` before the TOML profile exists, and the `operator`, `swap`, and `compressor` reason series of `ix_build_admission_blocked_seconds_total` until their respective producers exist. The absent pause series retains the declared `thermal` and `operator` reasons. These current-build omissions do not remove the series or labels from the metrics contract. The current-build lists above describe admitted stores; for an observed store the **Observe mode** rules below define which series exist, and `observe` is the producer of `ix_build_test_runs_total`. The closed `ix_build_builds_total` outcome set is an explicit exception to source-based omission: every outcome value is always emitted for every priority class, initialized to zero before a matching terminal event occurs, including abort outcomes.

For admission-blocked time, the complete `reason` set is `memory`, `swap`, `compressor`, `host_load`, `target_disk`, `operator`, and `probe`. `ix_build_admission_blocked_seconds_total` measures one host-wide interval, counted once regardless of waiter count, only while the scheduler's selected next eligible queued request is denied by a resource admission check. Time waiting only for capacity, FIFO or priority ordering, and all pause time is excluded. When multiple reasons apply to the selected request, use this complete precedence from highest to lowest: `probe` for a missing, invalid or stale host sample; `host_load`; `target_disk`; `memory`; `swap`; `compressor`; `operator`. While an operator hold or any pause is in effect this counter accrues under no reason, even when a resource limit also applies; `operator` stays in the reason set as FR-010's refusal reason, and its time is counted only in `ix_build_pause_seconds_total`. The exact current-build producer mapping is `memory` = `memory_reserve`, `target_disk` = `disk_reserve`, `host_load` = `host_load`, and `probe` = missing/invalid/stale host sample. Agent processes are counted by the profile's command patterns. Counters derive from persisted transition events, so they stay monotonic across restarts and prune. Labels exclude ticket ids, request ids, command text and environment. Reading metrics takes no admission decision and never blocks admission longer than the state-read time. A source that cannot be read is reported through `ix_build_probe_unavailable`, not as zero.

**Observe mode.** `locked-build observe [--kind build|test] [--priority check|test|gate] [--queued-at-ms N] -- <command...>` runs `<command...>` immediately. This mode only observes a command that an external wrapper has admitted; it never queues or admits work, checks capacity or resources, applies a priority, enforces a hold deadline, or terminates the observed command. The optional `--kind` and `--priority` values are metadata hints only and do not change execution or admission. A missing hint stays absent from the record and the export, with no placeholder value; the observer never infers kind or priority from command text and never supplies a default priority that appears real. A kind of `build` attributes the terminal result to build outcomes, and a kind of `test` attributes it to test-run outcomes. With no kind hint, the terminal result is recorded without a kind classification and increments neither outcome family. A build outcome increments a priority-labeled `ix_build_builds_total` series only when both `--kind build` and a `--priority` of `check`, `test`, or `gate` were supplied. A test-run outcome increments `ix_build_test_runs_total` only when `--kind test` was supplied. An absent priority never increments a priority-labeled outcome or queue-wait histogram. Queue wait is observed only when both `--queued-at-ms` and a valid `--priority` hint are supplied; the external wrapper supplies the timestamp at queue entry, before waiting, and the observer measures through command start. Without either option, no queue-wait observation is made. Occupancy of one slot is recorded while the command runs. The slot stays busy while the command is alive, even if the observer is dead. A live observer releases the slot when the command completes. If neither is verified alive (a reused process ID does not count) and no completion was recorded, the next `observe` invocation or metrics export no longer counts the slot, and no outcome, exit code or signal is recorded for it. An observed process maps exit code 0 to `ok` and any nonzero exit or signal termination to `failed`; observe mode records no other outcome value, because it has no source for a termination cause. It retains the raw exit code or signal separately from the outcome label.

An observed command is not an FR-005 request or lease: FR-005, FR-010 and FR-011 admission, ordering, hold, throttling, recovery signalling and termination do not apply to it. No locked-build process or command (`observe`, `serve`, a watchdog, `hold`, `resume`, `cancel`, `recover` or `prune`) originates a signal to the observed command or its process group.

An unrecognized observer option, a `--kind` or `--priority` value outside its set, or a `--queued-at-ms` value that is not a non-negative integer of Unix epoch milliseconds at or before command start emits one warning, is treated as not supplied, and never prevents or delays the command.

A failure after the command has started, including a failed or timed-out completion write, emits one warning, counts no outcome that was not durably recorded, and leaves the command's exit status or terminating signal unchanged.

On both the recorded and the fail-open path, the command SHALL keep the caller's exit status including signal termination, stdin, stdout, stderr, every other inherited file descriptor, environment, working directory, process group, signal dispositions and signal mask, and SHALL inherit no observer file descriptor. A signal sent to the process group reaches the command at least once. Each of SIGHUP, SIGINT, SIGQUIT, SIGTRAP, SIGABRT, SIGBUS, SIGSYS, SIGALRM, SIGTERM, SIGUSR1, SIGUSR2, SIGCONT, SIGURG, SIGXCPU, SIGVTALRM, SIGPROF, SIGWINCH and SIGIO sent only to the process ID the caller started is forwarded and reaches the command at least once; a group signal may be delivered a second time by forwarding, so each forwarded signal reaches the command at most twice. No other signal sent only to that process ID is forwarded. The caller-started process does not exit before the command has terminated, except when SIGKILL or a terminating signal outside that list is sent only to it. SIGKILL, SIGSTOP, SIGTSTP, SIGTTIN or SIGTTOU sent only to that process ID may not reach a separate command; stop signals may stop the observer while the command continues. Host wrappers SHALL send these signals to the command's process group or cgroup, and host adoption SHALL confirm it. Unless a signal has stopped the observer or its warning write to the caller's standard error blocks, no observer process keeps the command's stdio open more than 1000 ms after the command exits.

The observer SHALL start the already-admitted command before reading host configuration or touching observer state. A worker performs the bounded preflight: it validates configuration, acquires the state lock and records occupancy. The command does not wait for the worker. Any observer failure, including a missing or unwritable state directory, corrupt state, invalid configuration, lock timeout, or a store containing admitted requests rather than observed requests, emits one warning and leaves the command running. A preflight write already in progress at that warning can still complete; the only further write the observer makes is removal of the occupancy row that write added. The observer SHALL stop waiting for preflight state and configuration work 1000 ms after the preflight worker starts; that work can overlap command execution. When the command exits, waiting for an unfinished preflight and doing completion work SHALL share one 1000 ms interval, after which the observer abandons both. The state lock is released when each worker transaction completes. Its hold can overlap command execution, but command start and the signal-forwarding loop never wait for the lock. A store contains either observed requests or admitted requests, never a mixture. If modes are mixed, `observe` warns once and runs the command without changing the store. The configured-slots gauge for an admitted store uses the host configuration source above. The host configuration value SHALL be set to the number of build slots the external wrapper can admit; the observer neither measures nor enforces that number, and `ix_build_slots_busy` is exported unclamped when it exceeds the configured value. For `observe` and `metrics`, `capacity_units` and `maximum_units` are optional in the host configuration. Before the SWM-239 TOML profile exists, when `capacity_units` is absent, `ix_build_slots_configured` is omitted from Prometheus exposition and the JSON snapshot, never reported as zero. After that profile exists, TOML `[host].max_slots` remains the source for `ix_build_slots_configured`. `ix_build_slots_busy` continues to count every concurrently observed command without clamping to either optional value. This optional configuration does not make either field optional for `run` or any other command that queues or admits work; admitted work retains the existing configuration validation and admission behavior. In an observed store, overriding the closed-outcome-set zero initialization above, the **Build outcomes** paragraph below, and FR-015-AC-1, AC-8 and AC-9: `ix_build_builds_total` has only `ok` and `failed` series, for a priority only once a `--kind build` command with that priority has started; `ix_build_test_runs_total` has only `ok` and `failed` series, only once a `--kind test` command has started; `ix_build_queue_wait_seconds` has series only for a priority with at least one observation; and `ix_build_queue_depth`, `ix_build_admission_blocked_seconds_total`, `ix_build_pause_seconds_total` and `ix_build_paused_orphans` have no series. The Prometheus text and the JSON snapshot omit these values and never report them as zero. `run` and every other command that queues or admits work refuse an observed store with a request error and change nothing. The first recorded request fixes the store's mode, and `prune` does not reset it.

**Build outcomes.** `ix_build_builds_total` counts each request once, when it reaches a terminal [FR-005](FR-005-fair-build-scheduler.md) state; a restart, `recover` or `prune` does not count it again. Every `outcome` value is exported for every [FR-011](FR-011-priority-classes-lane-fair-share.md) priority class from 0, before any request ends with it, so a first occurrence reads as an increase. The `outcome` label takes one value from this closed set:

| `outcome` | How the request ended |
|---|---|
| `ok` | FR-005 state `succeeded` |
| `failed` | FR-005 state `failed`, with no FR-010 termination reason |
| `cancelled` | Cancelled while queued or running, with no FR-010 termination reason |
| `timed_out` | FR-005 state `timed_out` (hold deadline) |
| `aborted_memory` | Aborted above the memory `abort_above` |
| `aborted_swap` | Aborted above the swap `abort_above` |
| `aborted_compressor` | Aborted above the compressor `abort_above` |
| `aborted_host_load` | Aborted above the host-load `abort_above` |
| `aborted_thermal` | Aborted above the thermal `abort_above` |
| `rss_cap` | Terminated for exceeding its `rss_cap` |
| `pause_exceeded` | Cancelled for staying paused beyond `max_pause` |

A request whose recorded [FR-010](FR-010-scheduler-owned-throttling.md) end cause is a termination reason counts under that reason, spelled as in FR-010's table, in place of the value for its FR-005 state. Only the `abort_above` aborts begin with `aborted_`, so `outcome=~"aborted_.*"` selects exactly those; it does not select `rss_cap`, which a consumer names separately.
